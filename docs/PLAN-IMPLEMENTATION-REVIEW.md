# PLAN implementation review

Reviewed commit: `09da3c5b3d1e2cbfbd92bacb41ed629825c22b33`

This is a static repository audit against [PLAN.md](../PLAN.md). It does not certify a deployment. Live-only acceptance items are called out separately. The origin and intent of merged requirements are covered by the companion [PLAN history review](PLAN-HISTORY-REVIEW.md).

The repository partially implements the merged target. The main confirmed gaps are the ARR storage hierarchy, the omitted OpenVPN dataset, missing workload probes, incomplete mail-body redaction, incomplete static enforcement of Jellyfin integration restrictions, and absent destination-inbox acceptance. Section 22 also contains wording broader than the detailed alert design, while the implementation follows the more specific section 20 contract.

## Prioritized findings

### P1: ARR storage uses the remote backup layout instead of the local target

The active media defaults place Sonarr, Radarr, Prowlarr, qBittorrent, and the media library under `tank/secure/backup` ([defaults](../ansible/roles/media/defaults/main.yml#L14)). The shared catalog repeats those paths ([catalog](../ansible/service_catalog.yml#L13)). PLAN sections 17.3, 17.4, 17.28, and 24.1 require `no-backup`, so the deployed PV paths also resolve to the wrong hierarchy ([storage template](../k0s-services/arr/templates/storage.yaml.j2#L1)). The media role additionally hard-codes qBittorrent's backup path after using the defaults map elsewhere ([media tasks](../ansible/roles/media/tasks/main.yml#L89)).

Section 24 records a real branch conflict, but its instruction is to preserve the local no-backup target pending reconciliation ([PLAN](../PLAN.md#L338)). The implementation instead preserves the remote backup behavior. This affects backup scope, quota monitoring inventory, host paths, and any future recovery assumptions.

### P1: The required OpenVPN service dataset does not exist

Section 24.1 says every ARR service includes the OpenVPN gateway, while section 17.3 requires each ARR service to have a quota-controlled dataset and dedicated 10Ti PV ([PLAN](../PLAN.md#L208)). `media_services` and `media_datasets` omit OpenVPN ([defaults](../ansible/roles/media/defaults/main.yml#L4)), the storage template creates no OpenVPN PV/PVC ([storage template](../k0s-services/arr/templates/storage.yaml.j2#L1)), and the VPN Deployment mounts only host, Secret, and ConfigMap volumes ([workloads](../k0s-services/arr/templates/workloads.yaml.j2#L19)). The Zabbix dataset catalog therefore cannot monitor the required OpenVPN quota either ([catalog](../ansible/service_catalog.yml#L6)).

The PLAN is internally awkward here because the gateway currently has no apparent persistent state, yet section 24 explicitly retains the all-service dataset requirement. The implementation does not satisfy that retained target.

### P1: Several workloads do not have both readiness and liveness probes

PLAN section 22.1 requires readiness and liveness probes for every workload ([PLAN](../PLAN.md#L322)). Jellyfin has neither probe ([Jellyfin workload](../k0s-services/jellyfin/templates/workloads.yaml.j2#L41)). Guarded ARR applications have readiness only, so Sonarr, Radarr, Prowlarr, and qBittorrent do not restart on failed application health ([ARR workloads](../k0s-services/arr/templates/workloads.yaml.j2#L188)). The media VPN DNS container has readiness only ([ARR workloads](../k0s-services/arr/templates/workloads.yaml.j2#L66)). Alloy has readiness only ([Alloy deployment](../k0s-services/alloy/templates/deployment.yaml.j2#L36)). AmneziaWG, Cloudflare DDNS, and the Intel GPU plugin have no readiness or liveness probes ([AmneziaWG](../k0s-services/networking/templates/amneziawg.yaml.j2#L1), [DDNS](../k0s-services/networking/templates/ddns.yaml.j2#L1), [GPU plugin](../k0s-services/intel-gpu/templates/daemonset.yaml.j2#L1)).

Deployment availability checks do not close this gap because they run during installation and cannot restart an unhealthy container later.

### P2: Mail-body redaction is incomplete for multiline or structured bodies

The pipeline redacts credentials and common headers, but its `body|mail_body` expression consumes either a simple quoted string or one non-whitespace token ([Alloy config](../k0s-services/alloy/templates/configmap.yaml.j2#L233)). Ordinary JSON strings containing spaces are covered. Unquoted multiline bodies, nested JSON values, and JSON strings containing escaped quotes can leave content after the first matched fragment. This does not fully implement PLAN section 19.15's requirement to redact mail bodies before ingestion ([PLAN](../PLAN.md#L264)). Credential, authorization-header, cookie, and credential-bearing URL patterns are otherwise covered by the adjacent replacement stages.

### P2: Jellyfin's disabled-integration target is only partially encoded

The pre-start editor disables the plugin repository, installed plugin manifests, external-content suggestions, subtitle fetcher order, lyric fetcher order, metadata savers, and writes beside media ([helper](../media/jellyfin_helpers.py#L6)). This supports the plugin and subtitle portions while leaving online metadata fetchers intact. No repository setting explicitly identifies or disables the broader “remote-media integrations” required by section 18.9 ([PLAN](../PLAN.md#L245)). `EnableExternalContentInSuggestions=false` is narrower than disabling all remote-media integration surfaces. The exact behavior also depends on Jellyfin's generated configuration schema and needs live verification, which TODO already acknowledges ([TODO](../TODO.md#L13)).

### P2: Alert delivery is provisioned but destination receipt is not confirmed

OpenObserve provisions three severity rules and one heartbeat rule with a five-minute window, one-minute frequency, threshold one, and five-minute silence ([alert definitions](../logging/openobserve_helpers.py#L9)). Its email row includes level, namespace, service, and message, while the body includes alert name, row count, rows, and investigation URL ([alert template](../logging/openobserve_helpers.py#L33)). Disabled notifications disable managed rules ([provisioner](../logging/provision_openobserve.py#L9)).

However, PLAN section 22.11 requires confirmation at the destination inbox ([PLAN](../PLAN.md#L333)). The installer verifies heartbeat ingestion only ([logging role](../ansible/roles/logging/tasks/main.yml#L144)); inbox delivery remains explicitly outstanding ([TODO](../TODO.md#L21)). This is a known implementation gap rather than merely an unexecuted local check.

### Clarification: Section 22 notification wording is broader than section 20

Section 22.10 says every Warning-or-higher problem, recovery, and recurring reminder is emailed ([PLAN](../PLAN.md#L332)). The detailed section 20 contract assigns recovery and hourly reminder behavior to Zabbix ([PLAN](../PLAN.md#L295)), while OpenObserve severity rules evaluate matching row counts and use a five-minute silence ([alert definitions](../logging/openobserve_helpers.py#L51)). The implementation follows section 20, and this review does not classify the absence of OpenObserve recovery and reminder messages as a defect. The history review confirms that grouped log alerts replaced earlier per-event semantics and that the broad wording can be overread ([history review](PLAN-HISTORY-REVIEW.md#older-information-still-absent-or-abbreviated-in-planmd)). PLAN could clarify that section 22.10's recovery and reminder clauses apply to Zabbix problems.

### Clarification: `level=unknown` is a non-alert severity representation

The Alloy pipeline assigns `level="unknown"` to otherwise unclassified records and retains `level` among the allowed indexed dimensions ([Alloy config](../k0s-services/alloy/templates/configmap.yaml.j2#L229)). Managed rules match only `warn`, `error`, and `critical` ([alert definitions](../logging/openobserve_helpers.py#L9)), so `unknown` does not assign alert semantics or trigger severity notifications. Sections 19.12 and 22.4 could say “without a recognized alert level” if this representation is intended.

## Live-only validation boundary

Static evidence cannot establish ZFS import and unlock after reboot, actual k0s startup order, pod readiness on the target host, i915 allocation, certificate issuance and renewal, public and split DNS, firewall and VPN isolation, ARR/Jellyfin application behavior, database extension loading, retention after elapsed time, hardware telemetry, OpenObserve outage recovery, or inbox receipt. The repository has no local test or CI contract, and the supported verification path is `ansible/install.py` on a live host. This review did not run that installer or deploy resources.
